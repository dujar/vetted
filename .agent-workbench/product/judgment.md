# Judgment

## Round 1 — 2026-09-11, target: spec.md (with market.md and scout.md in evidence)

**What holds, said once:** the problem has a named sufferer and an ugly workaround (trust the listing UI, run a generic scanner, read one manual research post — and the issuer's own answer is a static docs page, market.md §6); "why now" is real (chain public 2026-07-01, AMC fight 2026-09-09, deadline 2026-10-04); the intersection market.md identifies — legitimacy verdict + power disclosure + execution-time refusal for tokenized stocks — is genuinely empty, not a graveyard; the verdict-discipline rules (positive evidence for IMPOSTOR, deterministic-only reverts, linked evidence) are the right shape and cover the demo false-positive case; the on-chain surface (registry + guard, ~300–600 LOC) is small enough to win the contract-quality criterion; Q7's Sepolia mirror already answers most live-demo fragility. Residual FP risk (a fresh official redeployment reads IMPOSTOR until attested) equals the docs page's own update lag — defensible in Q&A, not a hole.

H1 · differentiator untested against the incumbent that already covers this chain — "Generic scanners (GoPlus/De.Fi-style) … were shown to miss Robinhood Chain's beacon-proxy pattern and hidden modifier blocklists. (Evidence measured 2026-08-25)"
     market.md verified live that GoPlus's supported-chains API now returns `Robinhood / 4663` — the spec's own §Problem line "generic scanners have no economic reason to build per-chain logic for a 10-week-old chain" is half-false as written, and the load-bearing claim (coverage ≠ correctness) rests on a 3-week-old third-party blog post, not a re-test. A judge can paste the genuine token into GoPlus during Q&A; if it shows `is_blacklisted`/`transfer_pausable`/`is_proxy`, the risk-report half demos as a commodity. Answer: run GoPlus's API against the genuine tokens and the known impostor this week (Q9), and rewrite §Problem/§Risks-5 around "coverage ≠ correctness ≠ enforcement" before any code.

H2 · demo never touches the chain it claims to serve — "No reachable live official stock token for the demo — solved by self-deployed replica set (Q2)"
     The entire demo arc (impostor, canonical, blocklist) is self-deployed by the builder, and the IMPOSTOR verdict's ground truth is a registry the builder's own key attested — a judge can compress the demo to "you deployed both tokens and declared one real." The scanner is read-only RPC, so a live genuine token address is reachable even if a live swap is not; the arc never shows one. Answer: wire the IMPOSTOR ground truth to Robinhood's canonical list fetched live (market.md Q10) and put one read-only live-address scan in the 5 minutes, so the engine is seen judging chain data the builder did not deploy.

H3 · the demo proves the least-novel half and skips the most-novel half — "paste impostor → IMPOSTOR verdict … → guarded swap refuses the impostor on-chain, completes on the attested token"
     Impostor refusal is the feature adjacent tools approximate; upgrade-aware revocation is the feature nothing on the list has (the docs page cannot do it — that is the whole wedge per market.md §6), and the spec itself calls revocation "a feature, not a wart." Yet the 5-minute arc contains no beacon-upgrade moment: no staled webpage, no revoked attestation, no guard flipping. Q10 asks for exactly this and is unanswered. Answer: decide whether the upgrade-revocation beat is in the demo arc; if it costs more than ~a day of replica plumbing, say why the impostor beat alone carries "innovation" against a judge who has seen GoPlus + Blockaid + EAS.

H4 · PMF rests on an audience that may be near-zero and an enforcement path that is opt-in — "Who has it: retail users who hold or consider holding stock tokens on Robinhood Chain"
     The documented victim count is one novelty token; there is no cited case of anyone losing money to an impostor stock token, and on a 10-week-old chain with one explorer the population that pastes unlisted addresses into a checker today is tiny — while the guard protects only users who already route through it (a scammer's frontend never will; no third-party frontend integrates it in v1). WalletGuard's sunset (market.md §13) marks the consumer one-shot checker as a proven dead end. Answer: state the PMF story as "primitive others integrate + the filterer watchdog as the recurring audience" — and answer Q14 (promote the watchdog from roadmap to the retention slide) before building, because the roadmap slide is currently the only answer to "check once and leave."

H5 · scope: the hard research problem is silently scoped down, and the fallback path can double contract work — "scan any token address … and settle guarded swaps"; "Rust/Stylus (proposed) … Contingency: … all-Solidity on Robinhood Chain"
     "Hidden blocklist invisible in the ABI" is detectable in general only by research-grade bytecode analysis; in practice v1 will signature-match the known Robinhood pattern and fall back to UNVERIFIED-plus-heuristics for everything else — which is the honest design per verdict rule 1, but "scan any token address" overstates it and the spec should say the depth boundary out loud before a judge probes it. Second: if the week-1 spike half-fails (Stylus enabled but probe host fns missing or gas-prohibitive), Q3's fallback means rewriting every contract in Solidity inside weeks 2–3 of 3. Third: the replica suite is deployed and source-verified, so judges will read it as your contract quality — hold it to the same bar as the registry. Answer: write the depth boundary into §Scope, and pre-commit the spike's exact pass/fail test (probe staticcall + code-read host fn + gas) so the fallback decision lands day 7, not day 14.

H6 · three Q&A landmines are planted and un-defused — "Working name: Vetted … Trust layer for Robinhood Chain tokenized stocks" (one-liner); registry is bespoke with no EAS comparison anywhere in the spec
     Blockaid's homepage brand phrase is "the trust layer for onchain finance" (market.md §2) — the one-liner collides verbatim; a judge who knows EAS will ask "why not just EAS" and the spec never answers it (the honest answers — guard reads it in-tx, revocation semantics tied to probes — exist but are unwritten); Ondo's on-chain "attestations" mean EIP-712 trade quotes, inviting conflation (market.md §8). Q11/Q12/Q13 ask all three and are unanswered. Answer: pick the positioning now — drop "trust layer" from the one-liner, write the EAS paragraph (or put EAS underneath), and rename the registry fields to "canonical verification / token clearance." All three are afternoon fixes; all three cost real Q&A credibility if improvised on stage.
