> 1. **Escrow counterparty = the project MM key; `execute()` stays NO-ARG.** Two-party order shape rejected (would touch step-1's pinned abi.ts, step-5's shipped wallet.ts flow, and the shared fixtures — blast radius without benefit). Concretely: the buyer commits (guard escrows tokenIn via transferFrom) and calls `execute()` (the merged wallet.ts back-to-back two-tx flow); the guard holds a single configured counterparty address (the project MM key, set at construction); at execution the guard PULLS the MM's fill — tokenOut `transferFrom(counterparty → buyer)` for exactly `minOut`, requiring the MM's standing allowance — then releases the escrowed tokenIn to the MM. All five red-flag checks run before any movement; no error is ever swallowed, so EVM atomicity keeps every revert path at zero movement. Internal escrow invariants (amountIn==0, double commit, execute without an order) revert with dedicated non-`GUARD_*` errors — the five pinned strings stay reserved for the deterministic red flags.
> 2. **From-contract beacon resolution, pinned:** (a) beacon address source = extract the EMBEDDED beacon from the token's forwarder bytecode by calibrated shape (PUSH32 `0x7f` + 12 zero bytes + 20-byte address, with the `implementation()` selector `0x5c60da1b` appearing within the following 16 bytes — the genuine 283-byte forwarder's exact shape, `spike/evidence/p_proxy.hex`) — NOT codehash equality (step-6 replicas embed a different beacon at the same shape; the joint fingerprint stays shape-based); (b) implementation source = STATICCALL `implementation()` on that beacon — an external call, NOT a remote-storage read; (c) extraction failure ⇒ the blocklist and IMPL checks are SKIPPED for that token (never revert — an unverifiable shape degrades, it does not guess); `GUARD_IMPL_MISMATCH` reverts only when resolution succeeds and mismatches record.impl. The demo's upgrade→revocation refusal rides GUARD_RECORD_REVOKED (backend revocation trigger). Tasks 4/5 mocks mirror this mechanism exactly.
